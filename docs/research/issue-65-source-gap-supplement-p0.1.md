## Verification rule used here

1. A source may be cited **only for the claim it actually establishes**, read from the retrieved page or file, not from its title.
2. **Publisher or consortium public scope is not a licensed standard text.** Where a full standard was licensed or gated, this supplement says so and the standard stays an unverified candidate. No ISO/IEC text was read for this supplement.
3. Legal statements are quoted from primary legal text only, and each one is a statement about the cited jurisdiction's wording, **not** a Hylja policy decision and not legal advice.
4. Quotation is bounded and marked; anything paraphrased is labelled as a paraphrase. Where a PDF text layer was used, word spacing was normalized, so a reviewer must re-check the PDF before quoting further.
5. Retrieval status is recorded per source in the [verification log](#verification-log-retrieved-2026-10-01).

## The five roles the sources actually separate

The sources below never use Hylja's vocabulary, but they consistently separate five things that a flat enum would merge. These are **candidate meanings for human review**, in the spirit of the interview's glossary wording, not additions to [shared language](../../CONTEXT.md).

| Role | Candidate meaning | Where the sources separate it |
| --- | --- | --- |
| **entity** | A thing that exists in a domain: a component, a document, a revision of a document, a machining job, a load case, a configuration item, a server. | CFIHOS registers are lists of *documents and drawings* and of *tagged items* kept separately ([MDR](https://www.jip36-cfihos.org/wp-content/uploads/2024/10/v.2.0-CFIHOS-Specification-Document.docx), CFIHOS-DEF-18/19); NIST SP 800-128 distinguishes a Configuration Item from a Baseline Configuration. |
| **identifier** | A name, number or key that *resolves to* an entity. Its scope is usually the naming authority's own scope, not the open world. | CFIHOS requires document numbers "in conformance with the principal's document numbering specification" (CFIHOS-SPTR-56); OpenAPI requires `operationId` to be "unique among all operations described in the API", i.e. scoped to one description. |
| **property** | A value attached to an entity by an authority: a class, a type code, a status, a units statement, a classification code. | CFIHOS-DEF-22 calls a reference data library a "standard and unified naming convention for equipment classification, its properties, disciplines, and documents"; CFIHOS-DEF-13 treats an export-control classification number as an applied code, not as the item's kind. |
| **content** | The substance itself: the drawing body, the mesh, the program, the boundary-condition set, the contract terms, the baseline specification. | Sierra/SD numbers its input artifacts separately from the deck itself: "5.1. Input deck format", "5.2. Input Mesh Geometry File", "9. Boundary Conditions and Initial Conditions"; NIST SP 800-128: a Baseline Configuration is "a set of specifications for a system, or CI within a system". |
| **relation** | A typed link between entities: revision *of* document, load case *applies* boundary conditions, cross-reference *between* documents, change request *approved by* principal. These are first-class in every source read, and none of them is a value a string detector can classify on its own. | CFIHOS-DEF-1 ties "additional files" to "one document revision identification"; CFIHOS-SPTR-6 lists "relationships between data entities" as its own element; CFIHOS-SPTR-53 requires cross references to be "current, correct, and consistent". |

## Deterministic syntactic evidence versus bounded contextual ambiguity

The draft's `FORMAT` / `STRUCTURE` / `TENANT_DICTIONARY` / `CONTEXT` evidence kinds are consistent with what the sources above actually expose. Three rules follow, and they are proposals for the reviewer to accept, amend or reject:

1. **Global syntax can bound an artifact; it rarely names a subtype.** A CAE input deck and an NC program are text with recognisable overall syntax, but mesh geometry, boundary conditions, load cases, results files and feedrate values share no public grammar. Claiming `FORMAT` for them would be a claim about Hylja parser coverage that no source supports.
2. **Tenant-scoped naming has no global form.** CFIHOS numbering, discipline and document-type codes, and OpenAPI `operationId`, are all defined relative to a naming authority. For these, `TENANT_DICTIONARY` plus `STRUCTURE` is the only defensible evidence, and an absent, stale or foreign dictionary is an unresolved result, never a global guess.
3. **Ambiguity that must stay ambiguous.** Contextual evidence stays advisory and bounded: a bare number that may be a feedrate or an offset; a token that may be a revision code or a random string; a mesh path or a build artefact path; a hostname that may embed a person's name; a "load case" in prose or in a standards clause. In every such case the value keeps its protection and its ambiguity; a semantic judge may raise concern and may never select a treatment ([decision 003](../decisions/003-semantic-judgment-does-not-own-effects.md), [decision 009](../decisions/009-secrets-are-not-synthetic-identities.md)).

Deterministic syntactic evidence is therefore reserved for what is checkable without a tenant, a schema or a model: validated syntax of a national-ID **pattern** (never identity, and never asserted from a non-ID field), NC-program text shape, configuration-file syntax, endpoint and address syntax already in the codebase. Everything else in these five families is `STRUCTURE`, `TENANT_DICTIONARY` or bounded `CONTEXT`.

## Tenant ontology isolation

The sources make isolation a practical requirement, not only a security preference. CFIHOS makes identifiers a function of **the principal's own** numbering, tagging and contract-specific data library: CFIHOS-DEF-22 defines the reference data library as a naming convention for classes and properties, and CFIHOS-SPTR-7 makes delivery "in conformance with the contract RDL", a project-specific derivative. OpenAPI makes operation identity unique only inside one description. NIST SP 800-128 makes a baseline meaningful only inside the process that reviewed and agreed it.

Proposed consequences, for human review:

- **Public vocabularies are citations, not data.** Referencing CFIHOS, DEXPI, ISO or OPC classes in design discussion does not authorise importing their class lists into fixtures, dictionaries or a Hylja ontology. Any adopted vocabulary needs its own licensing and tenant-scope review.
- **Resolution scope stays tenant/project, like existing configured sources.** The codebase's configured-candidate mechanism is already bound to one tenant and project behind an opaque handle, and AGENTS.md makes cross-tenant resolution of a token, key, mapping or synthetic identity a security defect. A public RDL that could resolve an identifier in another tenant's input would be the same defect with a standards-body name.
- **Missing or out-of-scope vocabulary is unresolved, not permissive.** An absent, stale or foreign dictionary yields no match and no downgrade, mirroring the existing `PARTIAL`/`FAILURE` behaviour rather than a permissive global pattern.

## Privacy-context qualification, kept separate from classification

The verified GDPR wording supports treating personal-data status as an attribute of an **occurrence in context**, and supports treating combination effects as real. That is the same separation proposed in decision 010, so this supplement adds no new privacy vocabulary:

- Occurrence-level qualifiers remain tri-state `YES`/`NO`/`UNKNOWN`; `YES` may be raised by credible evidence, `NO` needs deterministic or trusted-context support, and a model's `NO` alone stays `UNKNOWN`. None of these is a legal determination.
- Relation-level qualifiers matter here more than in the original index, because three of the five gap families are relational. A maintenance row binds an address to a person; a document register binds a customer project to a revision history; an API description binds an operation identifier to a customer's internal system. Whether such a **structure** requires protection even when each component looks ordinary is an open design question recorded in the interview notes, and this supplement only supplies sources for the vocabulary, not the rule.
- Swedish personnummer and samordningsnummer handling stays where the index put it: semantic candidates plus a Swedish jurisdiction hint, with treatment and legal basis decided by qualified legal and policy humans. No number, valid or invalid, appears in this document.

## If a human review accepts parts of this: ADR and internal cutover implications

Nothing below may start before the [#65/#66 review gate](issue-65-66-independent-review-handoff-p0.1.md) records its verdict. It is written so that an accepted subset can be implemented without redesign.

1. **One decision record, not a silent edit.** Accepted roles (entity, identifier, property, content, relation), accepted candidate subtypes and the evidence-kind rules belong in a new decision record paired with decision 010, per AGENTS.md's one-fact-one-home rule. The unaccepted candidates stay in research documents.
2. **Coordinated internal cutover, no v1 reader.** As agreed in the third interview round, the project is unreleased: classification, policy selectors, oracle annotation schema and tests would be replaced together, with no backward-compatible reader, replay converter or old-record migration. Historical development and evaluation evidence keeps its producer version so it stays intelligible; that is bookkeeping, not compatibility.
3. **Digest and binding coverage.** Any new semantic, privacy or evidence field must fall inside the pinned classification digest and the trusted policy-request binding described in decision 010 and #66. A field outside the digest would let an integration substitute unverified semantics without detection, which is the same substitution failure #4's review found for candidate IDs and digests.
4. **Evidence provenance must record the new kinds.** Because several new candidates rest on tenant dictionaries and structure rather than syntax, provenance must distinguish `STRUCTURE` and `TENANT_DICTIONARY` claims from `FORMAT` claims so that evaluation can measure recognition methods separately.
5. **No #39 consequence without the protocol owners.** Candidate subtypes here are not oracle labels, not families, not surfaces and not denominators. Suggested additions belong to the evaluation owner under independent review, and none is made in this supplement.
6. **No parser claim.** Every row above is a vocabulary claim. Where a subtype later needs executable recognition tests before it can be called supported, that remains the reviewer's criterion.

## Residual gaps that remain human-only

- **Licensed standards.** ISO 10303 (AP242), ISO 10303-238 / 14649 (STEP-NC), ISO 19650, ISO 15489-1, ISO 14224, ISO 55000, IEC/ISA-5.1 and ISO 81346 could not be read. The ISO catalogue and Open Group documentation were **not readable** to an automated client in this session: the ISO catalogue pages did not return their documents, and the Open Group TOGAF/ArchiMate documentation URLs answered HTTP 200 with an account/sign-in page that carried no document text. No account requirement, licence or entitlement condition is claimed for any of them, and none was verified. Each needs a licensed or entitled reviewer.
- **A vendor-neutral CAE source.** The CAE evidence is one laboratory's solver documentation. Whether a neutral simulation data standard names the same objects is unverified.
- **Jurisdictions.** Only EU and US primary legal wording was verified, and only for definitions. Retention, privilege, works-council, defence-export and customer-contract regimes are unverified and out of scope here.
- **Domain generalisation.** CFIHOS describes capital-facilities handover in one industry; whether its vocabulary generalises to Hylja's target environments is an application-specialist question, not a source question.
- **Every acceptance question.** Family names, overlap precedence, relationship representation, privacy authority, escalation handling, fidelity predicates, review routing and the confidentiality-as-status question are all for the designated humans. Nothing above resolves them.
