# #39 synthetic corpus and protocol preparation — proposal p0.1

**Status: non-normative research draft; not a frozen v0 benchmark, fixture release, executable harness, or enforcement design.** Authority for this work is [issue #39](https://github.com/Marcus-Levin/hylja/issues/39) under [campaign #38](https://github.com/Marcus-Levin/hylja/issues/38); [evaluation policy](../evaluation.md) governs corpus handling, [plan](../plan.md#current-state) owns implementation status, and the [classification](../classification.md), [flow-control](../flow-control.md), [interaction](../contracts/interaction-envelope.md), [transformation](../contracts/transformation-contract.md), and [authorization](../contracts/authorization-contract.md) contracts supply vocabulary. This proposal does not amend those authorities. `p0.1` versions *this proposal only*; it is not a protocol version or a corpus hash.

## Proposed scope and family inventory

All examples and future fixtures for this campaign are obviously synthetic, non-routable, and disposable. The **proposed measured scope**, subject to revision before freeze, is observable text and bounded parsed fields at controlled `model.input`, tool, MCP, file, shell, and agent-handoff replay boundaries. Captured serialized body **and** metadata at the actual controlled sink are separate from candidate/classifier output. No-Jev reference evaluation is **evaluation-only and NON-ENFORCING**; it proves neither runtime interception nor authorization nor final-egress safety. Binary/opaque attachments, OCR/images, direct network paths and unobservable hosted/provider-side tool actions receive `unsupported` or `outside architecture` by role, not a pass. Coverage of any listed surface remains **untested** until an executable adapter/boundary is exercised.

The following IDs are *planning families*, not fixture IDs, allocated oracle labels, test cases, or scored coverage. Different held-out families must be authored with different workflow narratives, structures and cross-surface relationships, not generated by reseeding or lightly paraphrasing a development template.

| Development family | Proposed synthetic situations / utility contrast |
| --- | --- |
| D01 chat identities | PERSON NAME/EMAIL/PHONE, customer and project mentions; retain referential sense. |
| D02 diagnostic logs | User, host, documentation IP, port, non-live token-shaped placeholder, stack trace, correlation ID, nested payload; diagnose failure without exposing originals. |
| D03 structured data | JSON, XML, YAML, TOML, INI, dotenv, connection strings and environment dumps; keys/grammar/port values versus protected values, including protected keys. |
| D04 scripts and commands | PowerShell, Bash, BAT/CMD, Python and CLI arguments; preserve quoting, OS, executable, protocol and path semantics where allowed. |
| D05 config/code edit | Change a synthetic connection's port/protocol/path while maintaining valid syntax and host/customer cloaking. |
| D06 MCP exchanges | Observable call arguments, results, resources and prompts; distinguish hostile tool claims from trusted context. |
| D07 chained surfaces | File read → shell result → agent handoff and multi-turn alias consistency; planted values in both text and metadata. |
| D08 industrial taxonomy | Customer/project/plant/asset/drawing/item/functional-location identifiers and relationships; avoid needless cloaking of type/structure. |
| D09 contextual inference | Direct identifiers removed but synthetic combinations of date/site/asset attributes permit re-identification; assess generalization separately. |

| D11 brokered operation | Synthetic tenant/session-scope identity, authorized USE without DISPLAY, separately authorized DISPLAY, denied EXPORT, forged or cross-tenant reference; exact restoration only where permitted. |

**Blind-family allocation proposal:** H01–H04 are independently authored, private workflow families spanning, respectively, cross-surface task context, mixed representation, identity/inference and authorized-operation/failure behavior. This public index intentionally reveals no held-out cases, templates, exact labels, planted strings, prompts, task answers or family-specific constructions. Ensure class/surface coverage for both partitions without copying examples between them; resolve any impossibility *before* freeze, then lock family assignments. Neither a random row split nor a later copied production miss counts as a blind family.

### Public development-only illustration for #37

A disposable **development seed, not held-out data or a scored result**: tenant `TENANT-DEMO-A`, project `PROJECT-DEMO-01`, `owner=Demo Person Alpha`, `contact=person.alpha@example.invalid`, `callback=+1 202-555-0101`, `host=node.alpha.example.invalid`, `ip=192.0.2.17`, `port=443`. All are fictitious; `.invalid` and `example.invalid` are non-routable, `192.0.2.0/24` is documentation space and `555-0100`–`555-0199` are fictional numbers. Plant NAME in both configured, tenant/project-scoped and trusted field-hint contexts; plant EMAIL and PHONE in prose and parsed values without assuming they identify that NAME. Negative controls include a similarly spelled name under `TENANT-DEMO-B`, `port=443` and `status=1202` (not PHONE); include Unicode/escaped and overlapping representations with source-to-normalized span provenance. The independent oracle, not detector spans, says which mentions count. An unavailable semantic service must not erase local candidates; a later semantic label or independent sentinel catch must not retrofit a missed candidate as a hit. This sketches [#37](https://github.com/Marcus-Levin/hylja/issues/37) and [#40](https://github.com/Marcus-Levin/hylja/issues/40) comparison needs, not their implementation or success.

## Manifest design to implement and review before v0

Separate public protocol metadata from restricted fixture/oracle data; the initial example above is the only planted plaintext proposed for this public draft. The candidate-facing development fixtures may contain synthetic values; ordinary reports, CI captures, audit metadata and shared output must not contain planted originals, reversible maps, raw prompts, arbitrary metadata or complete held-out answers.

| Record / owner | Proposed fields and rule |
| --- | --- |
| Public scope/protocol manifest (protocol steward) | Future immutable version; in/out representation and surface matrix; roles and destination IDs; class/subtype vocabulary; profile/policy and allowed-fidelity definitions; task rubric and scoring denominators/weights/critical gates/abstention rules; split *family IDs*; pinned runner/config and candidate recording requirements. This proposal is not that manifest. |
| Synthetic corpus (fixture author, not candidate) | Opaque fixture ID, family ID, partition, source representation/media layers, authenticated caller/tenant/project/session/purpose, observed route and payload; fixtures created independently of candidate output. Restrict blind payloads and seeds to evaluator access. |
| **Independent planted oracle** (separate oracle author/reviewer) | Pre-candidate entity ID and occurrence IDs; exact planted synthetic original held privately; semantic type/subtype, sensitivity, trust/provenance and relationships; source field/path plus original and normalized offsets/encoding layers; explicit unplanted negatives; per-destination expected treatment, fidelity and allowed representation, critical-leakage gate, permitted restoration/operation and scope. Do not derive oracle records from candidate spans, judge classifications or sentinel catches. Resolve oracle disagreement before scoring. |
| Destination/treatment profile (policy reviewer) | Actual observed sink/profile/trust zone and authorized purpose; `KEEP`, `MASK`, `TOKENIZE`, `SYNTHETIC`, `GENERALIZE`, `REMOVE`, `BLOCK` or `REQUIRE_REVIEW` by planted record and destination. `BLOCK` stops and `REQUIRE_REVIEW` holds release, rather than transforming. Missing/mismatched context, unsupported protected content and required-check failure have an explicit restrictive outcome. A hosted judge request is a separate sink if ever used. |
| Independent task specification (task reviewer) | Prompt/config, pre-protection expected engineering answer or edit, syntax and fidelity predicates, relationship/identity-consistency checks, task-abstention rubric, destination and allowed tool effects. Pair comparable candidates on the same synthetic task, with a local synthetic task control; withheld prompts and answers stay restricted. Examples: diagnose port mismatch from log, produce a valid config edit, generate a path/protocol-correct script, identify a synthetic infrastructure relation. |
| Run and report (evaluator) | Candidate URL/commit/release, exact configuration/model/weights/question set, environment/hardware, date/tier/license, runner/protocol IDs and artifact integrity records; per class/family/role/surface/destination evidence, count/denominator and privacy-safe failure IDs. No raw payloads or mapping tables in ordinary reports. |

**Illustrative treatments only, not adopted policy:** for a proposed approved external model, a CONFIDENTIAL `PERSON.NAME` might be `SYNTHETIC` while a technical `NETWORK_IDENTIFIER.PORT` required for diagnosis may be `KEEP`; a `CREDENTIAL_OR_SECRET` defaults to `BLOCK` or irreversible `MASK`/`REMOVE` when the task may continue. For an arbitrary external sink, the same NAME can be `BLOCK`; a trusted authorized local USE operation may apply an original without giving DISPLAY or EXPORT. Only a reviewed, destination-specific manifest can fix these choices; a synthetic fixture may never itself assert a safer profile. Reversible NAME restoration is hypothetical until a brokered implementation exists. Preserve required grammar, port/protocol/OS/path and synthetic entity relationships only as expressly allowed; do not count blocking everything as utility-preserving.

## Proposed scoring and provenance distinctions

- **Candidate detection (before judgment/policy/sentinel):** per semantic class and separately `PERSON.NAME`, `PERSON.EMAIL`, `PERSON.PHONE`, report planted occurrence TP/FN and unmatched candidate FP with recall `TP/(TP+FN)`, precision `TP/(TP+FP)`, false-cloak/lookalike counts and subtype confusion. Predeclare normalized-to-source field/span matching and one-to-one overlap attribution; no matching after viewing held-out results. A missing local candidate remains FN after a judge or independent sentinel catches it. Zero denominators are `n/a`, not 100%.
- **Decision and actual escape:** compare per-destination treatments to the independently planted oracle; distinguish attempted plaintext released by the primary path but stopped by the sentinel from a **critical plaintext escape** in exact post-serialization bytes that reached a forbidden controlled sink. Inspect body, headers, metadata, errors and stream chunks with a separate planted-original check (including agreed bounded encoding equivalents); count blocked/held requests as zero bytes released but not as successful task runs. Report per-class protected-value containment recall as `forbidden planted occurrences not sent / forbidden planted occurrences presented for the tested sink` alongside the absolute escape count, sentinel catches, missed intercepts/bypasses, unauthorized restoration/tenant crossing, failures and contextual re-identification separately; define deduplication and multi-sink attribution before freeze. A candidate TP is not evidence of safe egress; zero observed escapes is bounded to tested profiles.
- **Utility and operational cost:** per task answer correctness, valid config/script syntax, required port/protocol/OS/path and relationships, identity consistency, over-cloaking, exact authorized restoration, abstentions/reviews, interventions and setup effort. Report latency/throughput and model/API/compute costs with hardware, denominator and environment. Do not average away a SECRET or other critical gate with utility.
- **Two evidence axes from #38:** per claim/role/surface use provenance `claim/docs`, `source-inspected`, `vendor-demonstrated`, `independently-executed`, or `untested`; separately outcome `pass`, `fail`, `observed-only`, `passthrough`, `unsupported`, or `outside architecture`. `untested` has **no observed outcome**. The original documented/source-inspected/executed/not-tested/unsupported terms map to these axes; only matching independent execution can substantiate a scored pass. Record a role-specific critical fail regardless of aggregate score.

## Blind access, integrity and freeze gate

**Pre-tuning baseline lock (pending):** Before *any* candidate tuning, independently author and review the planted oracle and negative controls, assign structurally independent development/held-out families, and freeze destination-specific expected treatments, allowed-fidelity and restoration rules **before tuning**, not merely before scored comparisons. Review and lock task expectations and the public scoring rubric, publishing its denominators, weights, critical gates and abstentions; version and integrity-record the actual baseline artifacts as a condition of this pre-tuning lock (none exist in this draft). Candidate developers may use development cases/labels and the public rubric but never blind held-out fixtures, oracle labels, task answers, salts/seeds or controlled-sink answers. A change to this baseline after tuning must be logged as a new baseline and must not silently reuse tuning or a compromised held-out family for comparable scored results. Desk/source research need not wait for this lock.

A separate evaluator controls the blind material. Do not place private material in this repository, PR artifacts or candidate worktrees; minimize CI logs, enable allowlisted counters/opaque IDs, version restricted blind corpus/oracle in a separately access-controlled evaluation store for reproducible reruns, and keep raw captures confined to disposable execution under a reviewed retention/deletion policy. Avoid committing raw held-out captures, reversible mappings, live credential-like strings or restricted real incidents. Audit evaluator access; never return blind labels to a candidate through error output or interactive tuning. After a scored run, release only a sanitized failure summary and optionally a **new** synthetic development regression; do not alter the frozen suite in place.

**Final scored v0 freeze (also pending, distinct from the pre-tuning lock):** #1 toolchain and the minimal runnable #5 seam must execute the already reviewed independent planted oracle, destination-specific expected treatments and at least one downstream engineering task end to end, using sufficient #2–#4 vocabulary. Demonstrate controlled exact serialized-byte capture, negative/failure behavior, candidate-event accounting and privacy-safe output; verify the supported/excluded surface matrix and locked critical gates/weights and held-out family independence. Only then version and cryptographically hash the exact scored public manifest, synthetic corpus, independent oracle, destination/policy and task configuration, partition and scoring plus runner/config; record each digest and runner identity with restricted results, exposing private digests only under an approved disclosure policy. Executability does not authorize post-tuning changes to the locked expected outcomes: any required change means a new baseline/protocol version and a fair new comparison with unexposed held-out families. No hash, executed score, adoption evidence, complete #39 claim or v0 freeze exists in this draft. Any subsequent change to corpus, scope, policy, oracle, task or scoring makes a new protocol version with an explanation; logged reproducibility reruns alone reuse v0. Scored [#40](https://github.com/Marcus-Levin/hylja/issues/40)–[#45](https://github.com/Marcus-Levin/hylja/issues/45) and [#47](https://github.com/Marcus-Levin/hylja/issues/47) comparisons wait for that freeze; [#48](https://github.com/Marcus-Levin/hylja/issues/48) must defer a critical unproved role. The lightweight #46 safety prescreen precedes third-party execution; full due diligence precedes adoption.
