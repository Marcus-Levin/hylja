# Source-to-sink policy decision contract

Status: draft foundation contract for issue #4. This documents the pure decision seam, **not** a deployment approval, adapter, broker, authorization proof, transformation, or egress control. Implementation status belongs only in [the plan](../plan.md#current-state).

## Inputs and authority

`decidePolicy(request, trustedBoundary, trustedBundle)` consumes separately supplied values. The `request` contains the normalized interaction's opaque reference, an opaque per-candidate `candidateRef`, subject, tenant/project/session/purpose, source, declared destination/profile, operation, composed classification, versioned policy reference and optional semantic recommendation. **Request content is not authentication:** the trusted adapter/broker must supply the independent `trustedBoundary`, after authenticating principal/workload, tenant and project membership, binding purpose/session, assigning a distinct privacy-safe candidate ID for each decision unit (not a raw span/field/value or model assertion), observing actual source trust and final routed destination including redirects, obtaining the independently pinned classification digest from a trusted composer handoff, and obtaining the committed policy identity/digest from a trusted control plane. Neither this module nor `createInteractionEnvelope` authenticates users, proofs, reviews or policy administrators. Never populate `trustedBoundary`, `trustedBundle`, or `trustedOutcome` from payload, wire metadata, a model, an untrusted caller or a self-asserted `CONTROL` claim. The `Classification` must come from the separately trusted classification pipeline, not envelope data. The trusted boundary pins a SHA-256 commitment to the *complete normalized classification* for that candidate; `digestClassification` rejects malformed records and `RESOLVED` without nonempty, structurally consistent detector evidence. Computing that digest from the untrusted request classification and placing it in the boundary would nullify the protection. These comparisons are congruence checks, **not** authentication of the composer, evidence producer, candidate identity or caller.

The supported foundation identity is exactly `hylja.foundation` version `1`; an unknown id/version is denied until reviewed code explicitly supports it. A trusted bundle contains destination profiles with exact actual sink kind/ref/trust-zone/profile-ID bindings, exposure (`LOCAL` or `EXTERNAL`), permitted treatments and a maximum *cleartext* sensitivity, plus explicit per-profile semantic class/sensitivity/source-trust/operation rules. There is no wildcard or default allow: absent, duplicate, ambiguous or malformed profiles/rules, or no matching rule, deny. The trusted boundary additionally provides an **independently pinned SHA-256 content digest** for the canonical bundle (including all profiles and rules), not only the public id/version. The pure `digestPolicyBundle` helper can compute this content commitment, but computing it from an attacker-supplied bundle and then calling it a trusted pin defeats the boundary. Version governance, bundle distribution integrity and keeping the pinned digest separate from the untrusted request are upstream obligations. Rule/profile array order does not change the canonical digest.

The source's influence trust is bound to the observed source and checked against classification provenance; it is independent of sensitivity. Classification `UNKNOWN`, `UNRESOLVED`, failed/conflicting evidence and absent records deny, even if a semantic signal says `KEEP`. For an external destination, `SECRET` or `CREDENTIAL_OR_SECRET` may only select irreversible `MASK` or `REMOVE`, and `KEEP` additionally requires an explicit rule, an approved profile and cleartext sensitivity at/below that profile's ceiling. `BLOCK` is terminal. `REQUIRE_REVIEW` is a held state; neither is a transformation. `SEND`, `USE`, `DISPLAY` and `EXPORT` require independent explicit rules: one operation never grants another. `USE` is **not** a brokered reveal permission; broker authorization remains separate.

## Review and replay

A pending decision has no bytes/effects and a SHA-256 **unkeyed replay fingerprint**, not a bearer credential, over the normalized policy/classification content and non-secret bound decision inputs, including the unique trusted candidate ID. Two separate candidates with the same class/sensitivity in one interaction must have different IDs and therefore different fingerprints; a review for A must not be applied to B. `decideReviewedPolicy` re-evaluates the *current* policy and compares the original held decision with that result. Only a **separately authenticated and authorized review outcome supplied by the trusted integration** can select one treatment from the rule's explicit review allowlist; it must match the same policy and classification content digests, candidate ID, interaction, source/trust, actual sink/profile, tenant/project, principal/workload, session, purpose and decision fingerprint. Missing/mismatched/invalid outcomes stay held; stale policy/rule/route/action or a removed review rule denies. A reviewer reference is for upstream attribution, not a self-authentication claim. External reviewer identity, approval authority, expiry/revocation, separation of duties and audit are outside this pure seam; the integration must enforce them. No path turns a semantic recommendation or forged review text into review approval.

Decisions expose only `state`, `treatment`, reason code and an optional unkeyed fingerprint; they never carry payload bytes, plaintext, mapping references, executable effects or a transport capability. Replay inputs (opaque per-candidate references, complete validated classification metadata, authenticated bindings and the trusted versioned policy snapshot) must be durable **non-secret** metadata; the integration must avoid putting protected values into candidate IDs, evidence provenance, source/sink refs or other identifiers. The implementation does not inspect or transform representations, prove synthetic/token quality, authorize uncloak, send bytes, handle streaming holdback, perform final serialized-byte egress checks or retain raw traffic. A `SELECTED` decision alone must not cause release: later transformation, broker checks where applicable, independent egress verification and enforceable adapters are separate mandatory gates. Unsupported/opaque content and unchecked alternate routes remain deployment coverage gaps, not implied approvals.

Threat coverage in this slice is limited to deterministic denial of missing/mismatched authenticated bindings, actual route/profile/version/content substitution, forged classification substitution, unresolved or structurally unsupported classification, untrusted semantic override and forged/stale or cross-candidate review transition. Its new surfaces are trusted bundle/profile lookup, separately pinned classification/policy digests, per-candidate identity assignment and review handoff. The synthetic class/trust/sink, sensitivity, tenant and review/property-style tests prove this function's choices, **not** end-to-end absence of protected bytes or production authorization; upstream caller authenticity, parser/detector recall, final serialization, transform fidelity, review authority and route interception need separate evaluation.
